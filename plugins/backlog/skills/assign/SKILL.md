## 目的

Backlog の課題単位で作業コンテキストを `.claude/<課題キー>/` に蓄積し、`/backlog:assign` を打つだけで「前回どこまでやったか」「次に何をするか」「どのブランチで作業するか」が揃った状態にする。

このスキルは**セッションの入口**として動く。長い調査や実装をこの中で始めてはいけない。状況を整えて、次アクションを提示したらユーザーにボールを返す。

## 状態

課題キーの解決・リポジトリとブランチの状態・課題ディレクトリの中身は、起動時にスクリプトが集めて下に埋め込む。同じ情報を Bash で取り直さない。

```!
node "${CLAUDE_SKILL_DIR}/scripts/assign.js" status "$ARGUMENTS"
```

## 進め方の原則

- `question`・`branchQuestion`・`upstreamQuestion` は、`label` と `description` をそのまま `AskUserQuestion` に渡す。文言や選択肢を作り直さない。
- 選ばれた選択肢の `run` を、そのまま Bash で実行する。`run` が `null` なら何もしない。git コマンドを自分で組み立てない。
- `run` の結果の `ok` が `false` なら、`message` を伝えて止まる（`next` があるときはそれに従う）。
- ユーザーが「Other」で選択肢にない指示をしたときだけ、その指示に従う（別の分岐元から切る、など）。
- 課題ディレクトリのフォルダとファイルは、スクリプト（`unit`・`file`）で作る。名前や番号を自分で決めて作らない。

## 手順

`upstreamQuestion` があるときは、どの手順よりも先に聞く（→「上流を付けない理由」）。

そのあとは `next` で決まる。

| `next` | すること |
|---|---|
| `stop-not-git` | git リポジトリでないことを伝えて止まる |
| `invalid-key` | `message` を伝え、課題キーを `AskUserQuestion` で聞き直す |
| `ask-key` | 課題キーを `AskUserQuestion` で聞く。答えが来たら `node "${CLAUDE_SKILL_DIR}/scripts/assign.js" status <課題キー>` で取り直し、その結果で続ける |
| `ask-create` | 1A |
| `fetch-requirement` | 1B、そのあと 2 |
| `propose-unit` | 1C、そのあと 2 |
| `summarize` | 1D、そのあと 2 |
| `summarize-legacy` | 1E、そのあと 2 |
| `error` | `message` を伝えて止まる |

### 1A. 課題ディレクトリが無い

**勝手に作らない。** リポジトリを間違えて起動したパターンが十分あり得るため、必ず `question` を聞く。ディレクトリ作成とブランチ作成はまとめて 1 回で聞く。

スクリプトが状況に合わせて選択肢を変えている。

- 課題キーを含むブランチが既にあれば、作り直さずにそのブランチへ切り替える
- 未コミットの変更があれば、stash してから着手する（未着手の課題なので、手元の変更は別課題のものである可能性が高い）

「他リポジトリを探す」の `run` は、`~/.claude/backlog.json` の `repos` を検索する。`found` にあるリポジトリを提示し、そこで作業するか確認する。見つからなければその旨を伝えて止まる。

「作成して着手」「ディレクトリのみ」の `run` の結果は `next: fetch-requirement` になる。`message` を伝え、1B に進む。

### 1B. 親課題の要求を取得する

Backlog MCP サーバーの課題を取得するツールで、課題キーの課題を取得する。本文（説明）を `requirementCommand` の標準入力にそのまま渡す。本文を整形したり要約したりしない。

```bash
node "${CLAUDE_SKILL_DIR}/scripts/assign.js" requirement PP-1234 <<'EOF'
（取得した本文）
EOF
```

スクリプトが「## 要求」セクションを取り出して `00_サマリー/要求.md` に書き込む。

- 「## 要求」が無ければ `next: ask-section` と `question` が返る。見出しの一覧が選択肢になっているので、そのまま聞く。選ばれた選択肢の `run` は、本文を渡し直さなくても動く
- 書き込めたら `next: propose-unit` になる。1C に進む

Backlog MCP サーバーは取得にだけ使う。課題の更新・コメントの追加など、Backlog への書き込みには使わない。

### 1C. 最初のユニットを提案する

`00_サマリー/要求.md` を読み、最初のユニットの名前を提案して確認する。名前は作業の内容が分かる短い言葉にする（例: 「ログイン不具合の修正」）。

確認できたら次を実行し、そのユニットの `要求` を書いてから、着手点を 1 つ提案する。

```bash
node "${CLAUDE_SKILL_DIR}/scripts/assign.js" unit PP-1234 "ログイン不具合の修正"
node "${CLAUDE_SKILL_DIR}/scripts/assign.js" file PP-1234 要求
```

### 1D. 前回の続きをまとめる

`CLAUDE.md`（リポジトリ直下・`.claude/`・`~/.claude/`）はセッション開始時に自動で読み込まれているので、重複して読み直さない。

`issueDir.summaryStale` があるときは、まとめる前に、そこに並んだ閉じたユニットの内容をサマリーに反映する（→「ユニットの操作」）。

読む対象:

- サマリー: `issueDir.summary.files` に並んでいるファイル（`要求`・`進捗`・`やること` を優先）
- 最新のユニット: `issueDir.units` の最後の要素の `files`
- コミット履歴: `log`

閉じたユニットは、サマリーに反映済みなので読まない。経緯を確認する必要があるときだけ読む。

読んだら、**短く**まとめて次アクションを出す。全文の再掲はしない。

```
# PP-1234 <件名>

- 状態: <どこまで終わっているか 1〜2 行>
- ユニット: <最新のユニットの名前>（<書いてあるステージ>）
- ブランチ: `PP-1234`（チェックアウト済み / 未チェックアウト / 未作成）
- 未コミットの変更: <あり（ファイル数）/ なし>

次の候補:
1. <具体的な作業。ファイル名・関数名レベルまで書く>
2. <同>
3. <同>
```

ブランチと未コミットの変更の行は、`branch` と `dirty` の値をそのまま使う。

次候補は憶測で埋めない。`やること.md` の未実施項目、最新の `進捗.md`、最新のユニットの書きかけのステージ（`unfilled`）とまだ無いステージ（`missing`）、コミット履歴の流れ、書きかけのコードから拾う。拾えるものが無ければ「前回の作業記録がないので要求から起こした」と明示した上で、`要求.md` から妥当な着手点を 1 つ提案する。

### 1E. 古い構成の課題をまとめる

`親課題.md` と `ver.X` の古い構成の課題。`issueDir.files` に、カテゴリごとの最新版（番号の大きい `ver.X` から遡って最初に見つかったもの）が並んでいる。それを読んで 1D と同じ形でまとめる。

新しい構成への移行は、ユーザーから頼まれたときだけ行う。

### 2. ブランチの確認

ブランチ名は課題キーそのもの（`PP-1234`）。prefix は付けない。分岐元は `origin/hotfix`。

例外として、親課題と子課題をまとめて扱う場合に `PP-1234_PP-1235`（親_子）のような複合名がある。担当者が子課題ごとに分かれるケースで使われる。スクリプトはこの形も拾う。

`branchAction` が `none` なら作業できる状態なので何も聞かない。それ以外は `branchQuestion` を聞き、選ばれた選択肢の `run` を実行する。

| `branchAction` | 状況 |
|---|---|
| `ask-switch` | 課題キーを含むブランチが 1 つある |
| `ask-choose` | 複合名などで複数ある |
| `ask-create-branch` | どこにも無い。`run` が `origin/hotfix` から `--no-track` で作成する |

未コミットの変更があると、スクリプトは「stash して〜」の選択肢を加える（`ask-choose` は選択肢の数の上限のため加えない）。stash は `.claude/` を対象から外す。

親課題・子課題をまとめる意図がユーザーから示されたときだけ `PP-1234_PP-1235` 形式を新規作成の候補にする。こちらから複合名を持ち出さない。

## ユニットの操作

スキルの起動後の作業中も、課題ディレクトリはこの操作で扱う。

| 操作 | コマンド |
|---|---|
| 次のユニットを作る | `node "${CLAUDE_SKILL_DIR}/scripts/assign.js" unit PP-1234 "<ユニットの名前>"` |
| 最新のユニットにステージのファイルを作る | `node "${CLAUDE_SKILL_DIR}/scripts/assign.js" file PP-1234 <ステージ>` |
| サマリーにステージのファイルを作る | `node "${CLAUDE_SKILL_DIR}/scripts/assign.js" file PP-1234 <ステージ> --summary` |

- 新しいユニットを作るのは、前のユニットの要求に対する作業が終わり、別の要求が出てきたとき。例: 実装の AI レビューで問題が見つかった → 「AI レビュー指摘の修正」のユニットを作り、レビューの結果を基に `要求` を書く
- `unit` を実行すると、それまでのユニットは閉じる。閉じたユニットへの書き込みは hook が拒否する。直す必要があれば、最新のユニットに書く
- `unit` の結果が `next: reflect-summary` のときは、閉じたユニット（`closed`）の内容をサマリーの各ファイルに反映する。サマリーは書き換えてよい
- ファイルは必要になったときに作る。作ったが使わないステージには「該当なし」と書く。雛形のまま残さない

## ファイル構成

```
.claude/PP-1234/
├── 00_サマリー/                    今の状態。書き換えてよい
│   ├── 要求.md                      親課題の「## 要求」（スクリプトが Backlog から取得する）
│   ├── 調査および要件定義.md
│   ├── 実装.md
│   ├── PR本文.md
│   ├── ...
│   ├── 進捗.md                      セッションごとの進み具合
│   └── やること.md                  未決事項、上長確認事項、未実施項目などを書く。やったことは削除する
├── 01_ログイン不具合の修正/         閉じたユニット。書き換え禁止
│   ├── 要求.md
│   ├── 調査および要件定義.md
│   └── 実装.md
└── 02_AI_レビュー指摘の修正/        最新のユニット。書き換えてよい
    └── 要求.md
```

ステージのファイル（ユニットとサマリーの両方で使える）:

| ステージ | Backlog |
|---|---|
| 要求 | 親課題 |
| 調査および要件定義 | 子課題 |
| 実装 | 子課題 |
| PR本文 | （GitHub の PR） |
| AIレビュー | |
| 第三者テスト | 子課題 |
| 開発者確認 | 子課題（時々使う） |
| リリース後の動作確認 | 子課題 |

`進捗` と `やること` はサマリーにだけ置く。

`file` は、`調査および要件定義`・`実装`・`PR本文` を次の雛形で作る。ほかのステージは空のファイルで作る。

`調査および要件定義.md`:

```markdown
## 仕様の調査

（要求に基づいてコードなどを調査した結果を書く）

## 要件定義

（仕様の調査の結果を基に、要件定義を行う）
```

`実装.md` と `PR本文.md`:

```markdown
## 概要

（概要を書く）

## 詳細

（項目に分けて詳細を書く。項目ごとの内容が多い場合は ### で、少ない場合は箇条書きで書く）
```

`PR本文.md` には、変更したファイルやコミットの一覧、差分など、GitHub の画面から分かることは書かない。また、他のマークダウンへの参照も書かない（マークダウンは git 追跡の対象外のため）。

強調にイタリックやダブルクォートを使わず、引用は「」、書名や画面名は『』、コードやパスはインラインコードを使う。社内 Wiki の記法に揃えておくと、そのまま Backlog に転記しやすい。

## 上流を付けない理由

`git switch -c PP-1234 origin/hotfix` と書くと、分岐元がリモート追跡ブランチであるため
`branch.autoSetupMerge`（既定値 `true`）が働き、**上流が `origin/hotfix` として記録される**。

```
branch.PP-1234.remote origin
branch.PP-1234.merge  refs/heads/hotfix   ← 課題ブランチなのに hotfix を追跡
```

このリポジトリの運用では、課題ブランチの上流は**最初の `git push -u origin PP-1234` で自分と同名に付く**。
push 前の正しい状態は「上流なし」であり、`origin/hotfix` を追跡している状態は誤り。

実害は `git pull` に出る。PP-1234 で作業した後に `git pull` すると、**hotfix の他人の変更が黙って混ざる**。

```
$ git reflog show PP-1234
e6973ec5 PP-1234@{0}: merge origin/hotfix: Fast-forward   ← 意図しない取り込み
cda7c434 PP-1234@{1}: branch: Created from origin/hotfix
```

push 側は `push.default` の既定値 `simple` が上流名の不一致を検出して拒否するため、
hotfix に push されることはないが、毎回エラーで止まる。

スクリプトの `run` は、課題ブランチを常に `--no-track` で作成する。

**すでに付いてしまっている場合**は、`status` が検出して `upstreamQuestion` を出す。「外す」の `run` が `git branch --unset-upstream PP-1234` を実行する（PP-1234 に独自コミットがあっても安全。ローカル設定を消すだけ）。

なお `branch.autoSetupMerge simple` を設定済み

## 注意点

`.claude/` は git の追跡対象外。つまり:

- `.claude/PP-1234/` の内容はこのマシンにしか存在しない。壊すと復元できないので、閉じたユニットは書き換えない（hook が Edit・Write を拒否する。Bash でも書き換えない）
- ブランチを切り替えても `.claude/PP-1234/` は消えない。ブランチと課題ディレクトリは独立しているので、別課題のブランチにいるまま前の課題のディレクトリを読むこともできる
- 追跡外なので `.gitignore` やコミット漏れを気にする必要はない。その手の確認や注意喚起はしない

## 設定

会社固有の値は `~/.claude/backlog.json` に置く（このプラグインは公開リポジトリにあるため）。

```json
{
  "repos": ["C:/path/to/repo1", "C:/path/to/repo2"]
}
```

`repos` は「他リポジトリを探す」で検索するリポジトリのルート。
