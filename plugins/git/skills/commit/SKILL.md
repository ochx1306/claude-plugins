## 目的

コミットの粒度、メッセージの書式、内容を毎回そろえる。機械的に判定できることはスクリプトと hook に任せ、AI は粒度の判断とメッセージの本文に集中する。

## 原則

- 対象のファイルは常に `git add <パス>` で明示する。`git add -A`、`git add -u`、`git add .`、`git commit -a` は使わない。
- `--no-verify` は使わない。コミット前のフックが失敗したら、原因を報告して指示を待つ。
- push 済みのコミットの `--amend` と force push は、ユーザーが明示的に指示したときだけ行う。
- `git push` は、指示されたときだけ行う。

## 手順

### 1. 状況を確認する

```sh
node "${CLAUDE_SKILL_DIR}/scripts/commit.js" status
```

| 項目 | 見ること |
|---|---|
| `staged`、`unstaged`、`untracked` | 3 種類の変更を分けて把握する |
| `stagedSignals`、`untrackedSignals` | 機密の可能性、生成物、コミットしない資料、`.gitignore` |
| `operation`、`detached` | merge や rebase の途中か、HEAD がブランチを指していないか。該当すれば先にユーザーに確認する |
| `protectedBranch` | 保護ブランチか。該当すれば、最初にそのことをユーザーに伝える |
| `format` | タイトルの書式。`null` なら書式の指定はない |
| `recentSubjects` | 既存のメッセージの言語と文体。これに合わせる |
| `configError` | 設定の問題。あればユーザーに伝えて止まる |

中身は `git diff` と `git diff --cached` で読む。

### 2. 課題キーを決める

`format` が課題キーの形式のときだけ行う。次の優先順で決める。

1. ユーザーが指定したキー
2. 会話で扱っている課題のキー
3. `issueKeys.branch`（ブランチ名に含まれるキー）
4. `issueKeys.directories`（資料のディレクトリ名）

候補が食い違うか、1 つも特定できないときは、推測で付けずにユーザーに確認する。

### 3. 粒度を決める

基準の優先順は次のとおり。

1. ユーザーの指定（引数の指定を含む）
2. 課題の要件や作業メモに書かれた作業の単位
3. リポジトリの規約（CLAUDE.md、CONTRIBUTING）
4. 既定: 1 コミットは 1 つの意味的に完結した変更。そのコミットだけを revert しても筋が通る状態にする

次のどれかに当てはまれば、分割を検討する。

- 変更が複数の課題にまたがっている（必ず分ける）
- 機能の追加やバグの修正と、リファクタリングや整形が混ざっている
- 独立して説明できる変更が 2 つ以上ある
- タイトルが「〜と〜」「ついでに〜」「〜、および〜」になる
- ライブラリの更新、生成物、設定の変更が、実装の変更と同じコミットにある

次のものは分割しない。

- 同じ変更に必ず伴う修正（呼び出し元の追従、型定義、テスト、マイグレーション）
- 分けるとビルドや動作が壊れるもの

独立性を判断できないときは、1 コミットにまとめず、分割案を 2〜3 通り示して選んでもらう。

### 4. 未追跡ファイルを仕分ける

未追跡ファイルは、次のどれかに分けてユーザーに示す。

| 種類 | 対応 |
|---|---|
| 今回の実装に必要な新しいファイル | `git add <パス>` する |
| 調査メモ、設計資料、スクリーンショット、一時ファイル | コミットしない。メッセージからも参照しない |
| ignore すべきもの（ログ、ビルドの生成物、IDE の設定） | `.gitignore` への追加を提案する（別のコミット） |
| 判断できないもの | ユーザーに確認する |

### 5. メッセージを書いて検査する

メッセージをリポジトリの外の一時ファイル（スクラッチパッドなど）に Write で書く。対象のファイルをステージしてから検査する。

```sh
git add <パス> <パス>
node "${CLAUDE_SKILL_DIR}/scripts/commit.js" check --message <メッセージのファイル>
```

既存のコミットを直すときは、`check` に `--amend` を付ける。

メッセージの内容は次のとおりにする。

- タイトルは 1 行で、何がどう変わったかがわかるように書く。
- 本文は必要なときだけ、タイトルとの間に空行を 1 行入れて書く。なぜそうしたか、差分だけではわからないことに限る。
- 環境から署名の行（`Co-Authored-By` など）を指定されていれば、メッセージの末尾に付ける。

結果の扱いは次のとおり。

- `errors`: すべて直して検査し直す。`ok` が `true` になるまでコミットできない。
- `warnings`: 誤検出を含む。内容を確認し、問題があるものだけ直す。残すものは、次の手順でユーザーに理由を伝える。
- `staged`、`unstaged`、`untracked`: 入れるはずのファイルが `staged` にあり、余計なファイルがないことを確認する。新しいファイルの入れ忘れに注意する。

スクリプトで判定できない次の点は、AI が確認する。

- メッセージに書いた内容がすべて差分にあり、差分の変更がメッセージから漏れていない。漏れていれば手順 3 に戻る。
- 試行錯誤や採用しなかった案を書いていない。設計判断の理由は、最終状態の説明として書く。
- チャットのやり取りや、リポジトリにない資料を前提にしていない。

### 6. 提示して実行する

コミットの単位ごとに、対象のファイルとメッセージをユーザーに示してから実行する。実行すると Claude Code の確認ダイアログが出るので、これをユーザーの承認とする。チャットでの返事は待たない。

```sh
git commit -F <メッセージのファイル>
```

- `git commit` は他のコマンドと続けず、単独で実行する。
- `git commit` に指定できるのは `-F`、`--amend`、`-q` だけ。
- `check` のあとでメッセージかステージ内容を変えたら、検査し直す。
- 複数のコミットに分けるときは、コミットごとに手順 5 と 6 を繰り返す。

実行後は `git log --oneline -3` で結果を報告する。

## 拒否されたとき

hook の理由に従って手順に戻る。検査を回避するために、コマンドの形を変えて再実行しない。

merge や rebase の途中でコンフリクトを解消したあとのコミットは、このスキルの対象ではない。git が用意したメッセージのまま、通常の手順で完了する。

## 設定

`~/.claude/git.json` に書く。ファイルがなければ既定値を使う。`repos` の `path` に一致するルールのうち、最も長いものを最上位の設定に重ねる。

```json
{
  "commit": { "format": "conventional" },
  "repos": [
    {
      "path": "C:/dev/example-company",
      "protectedBranches": ["release", "develop"],
      "commit": { "format": "issue-key", "ignoredPaths": [".claude/"] }
    }
  ]
}
```

| 設定 | 意味 | 既定値 |
|---|---|---|
| `protectedBranches` | コミットやマージの前に確認するブランチ | `[]` |
| `commit.enforce` | スキルを通さない `git commit` と、対象を明示しない `git add` を拒否する | `true` |
| `commit.format` | タイトルの書式。`none`、`conventional`、`issue-key` | `none` |
| `commit.pattern` | タイトルの書式の正規表現。`format` より優先する | `null` |
| `commit.ignoredPaths` | コミットしない資料のパスの前方一致。ステージとメッセージからの参照を拒否する | `[]` |
| `commit.titleMaxLength` | 警告するタイトルの長さ。書式の接頭辞は数えない | `50` |
| `commit.maxFiles` | 警告するファイル数 | `50` |
