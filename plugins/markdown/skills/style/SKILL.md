## 目的

日本語の Markdown 文書を、決められた記法ルールに沿って書く・直す。記法は GFM（GitHub Flavored Markdown）を前提にする。README などのリポジトリ内の文書、社内 Wiki（Backlog Documents など）、Issue や PR の本文のどれにも使う。

モードは 2 つあり、入力から判断する。

- 作成モード: 「〜のページを書いて」「〜の手順をまとめて」など、新しい文書を作る依頼。ルールに沿った Markdown を出力する。
- レビューモード: 既存の Markdown を渡されて「見て」「直して」「おかしいところある？」と聞かれたとき。指摘レポートと修正済みの Markdown を出力する。

どちらとも取れるとき（既存の文を渡されて「これを膨らませて」など）は、決めつけずに確認する。

## 文書の種類

H1 の扱いだけは、文書がタイトルを本文と別に持つかで変わる。最初に判断する。

| 種類 | 例 | H1 |
|---|---|---|
| タイトルを別に持つ | 社内 Wiki、Issue・PR の本文、frontmatter のある文書（SKILL.md など） | 使わない。本文は `##` から始める |
| 単体の文書 | README、`docs/` の文書 | 先頭に 1 つだけ置き、タイトルにする |

貼り付けられた Markdown は、どこに貼るものかで判断する。わからなければ確認する。

## 検査スクリプト

機械的に判定できるルールは、スクリプトで検査する。AI は検出結果の確認と、スクリプトでは判定できないルールの判断に集中する。

```bash
node "${CLAUDE_SKILL_DIR}/scripts/check.js" <ファイル>
```

タイトルを別に持つ文書には `--no-h1` を付ける。frontmatter のあるファイルは、付けなくても同じ扱いになる。

貼り付けられた Markdown は、標準入力にそのまま渡す。

```bash
node "${CLAUDE_SKILL_DIR}/scripts/check.js" --no-h1 - <<'EOF'
（Markdown）
EOF
```

1 件 1 行で `<ファイル>:<行> [<ルール>] <内容>` を出力する。問題がなければ何も出力しない。

| ルール | 検出するもの |
|---|---|
| `h1` | 先頭以外の H1。`--no-h1` ではすべての H1（`#` と `===`） |
| `h4` | `####` の見出し（使ってよい場合かは AI が確認する） |
| `h5` | `#####` 以上の見出し |
| `heading-skip` | レベルを飛ばした見出し（H1 の次の `###` も含む） |
| `italic` | `*…*`、`_…_`、`<em>`、`<i>` |
| `double-quote` | 日本語の文の中の `"`、`“`、`”`（英文の中の引用は対象外） |
| `fullwidth-bracket` | 全角の `［］` |
| `space` | 和文と英数字・インラインコード・UI 要素の `[ ]` が、スペースなしで接している箇所 |
| `fullwidth-alnum` | 全角の英数字 |
| `halfwidth-kana` | 半角カナ |
| `list-period` | 文末の「。」の有無が混ざったリスト |
| `code-lang` | 言語を指定していないコードブロック |
| `link-text` | 「こちら」「ここ」のリンクテキスト |
| `broken-link` | 空のリンク先、存在しない相対パスのファイル（大文字と小文字の違いも含む） |
| `broken-anchor` | 存在しない見出しへのアンカー（`#概要`、`other.md#概要`） |
| `image-alt` | 代替テキストが空の画像 |
| `github-alert` | GitHub のアラート（`> [!NOTE]` など） |
| `bold-quote` | ボールドと「」『』の重ねがけ |
| `bold-line` | 行全体がボールドの行（見出しの代わりにしている行も含む） |
| `definition-list` | `: ` で始まる定義リストの行 |
| `details` | 折りたたみ（用途が妥当かは AI が確認する） |
| `unclosed-fence` | 閉じていないコードブロック（参考） |

frontmatter、コードブロックとインラインコードの中、HTML タグの属性は検査しない。誤検出はあり得るので、検出結果は内容を見て確認する。

リンク先は次のように確かめる。

- 相対パスは、検査するファイルからの位置で確かめる。標準入力では基準がないので、同じ文書内のアンカーだけを確かめる。
- URL と `/` で始まるパスは確かめない。URL の接続先は検査の対象外で、`/` で始まるパスは表示する環境で解決先が変わるため。
- アンカーは GitHub の生成規則で判定する。Wiki など規則の違う環境の文書では、`broken-anchor` が誤検出になることがある。

## 記法ルール

作成モードとレビューモードで共通の判定基準。理由も含めて理解し、ルールの意図に沿って判断する。

### 見出し

- H1 は文書のタイトルにだけ使う（→「文書の種類」）。タイトルを別に持つ文書に H1 を置くと、表示でタイトルが二重になる。
- `##` はセクション（「概要」「手順」など）、`###` はセクション内の細分に使う。
- `####` は、同じ構成の項目を並べるときだけ使う。例: API リファレンスで、関数ごとの `###` の下に「引数」「戻り値」の `####` を繰り返す。それ以外で 3 階層目が必要なら、`###` の下を見出しでなくリストやテーブルにするか、文書を分割する。
- `#####` 以上は使わない。
- 見出しのレベルを飛ばさない（`##` の次に `####` を置かない）。アウトラインが壊れ、スクリーンリーダーや目次の生成が誤動作するため。

### 強調と装飾

役割ごとに使う記法を 1 つに決める。同じ役割に複数の記法を混ぜない。

| 役割 | 記法 | 例 |
|---|---|---|
| ファイル名・パス・コマンド・設定値・識別子 | インラインコード | `` `/etc/hosts` `` を編集する |
| UI 要素（ボタン・メニュー・画面名） | 半角の `[ ]` | [ファイル] メニューの [保存] を押す |
| 語句の言及・用語の初出・短い引用 | 「」 | 仕様書に「〜」とある、この操作を「冪等」という |
| 記事・章・論文の題名 | 「」 | 「障害対応」の章 |
| 書籍・雑誌・新聞・マニュアルなどの題名 | 『』 | 『運用マニュアル』の「障害対応」の章 |
| 「」の中の「」 | 『』 | 「仕様書に『必須』とある」と指摘された |
| 製品名・サービス名・組織名 | 装飾しない | GitHub の Issue |
| 外国語の語句 | 装飾しない | de facto の標準 |
| 警告・必須事項 | ボールド（語句単位で少量） | `**削除すると復元できません**` |
| 長い引用 | 引用ブロック `>` | |

ボールドや引用符で書かれがちなファイル名・コマンド・設定値は、ほぼすべてインラインコードにできる。迷ったらまずインラインコードを検討する。

UI 要素の `[ ]` は、前後の和文との間に半角スペースを入れる（→「文字」）。直後に `(` や `[` を続けるとリンクとして解釈されるため、続けない。全角の `［］` は使わない。

### 強調の乱用

強調は、記法の選び方よりも使いすぎで崩れる。

- 文や段落をまるごとボールドにしない。強調は語句単位にする。
- ボールドだけの行（`**注意**` など）を見出しの代わりにしない。見出しにするか、続く文の語句をボールドにする。見出しの代わりのボールドは目次やアウトラインに出ず、見出しの階層も崩れる。
- ボールドと「」を重ねない。
- 警告・必須事項以外にボールドを使わない。すべてボールドにすると、どれも目立たなくなる。

### 使わない記法

- イタリック: 日本語のフォントは斜体の字形を持たず、ブラウザが機械的に傾けるだけなので読みにくい。英語の文書でイタリックを使う場面（書名、強調、用語の初出、外国語の語句）には、それぞれ「強調と装飾」の表の記法を使う。
- ダブルクォーテーション（`"`、`“`、`”`）: 日本語に混ざると字面が崩れ、全角の幅もそろわない。日本語の文では「」にする。英文の中の引用はそのままでよい。
- 定義リスト（用語の次の行に `: 説明`）: CommonMark・GFM の標準ではなく、表示する環境によっては描画されない。用語と説明は 2 列のテーブルにする。
- GitHub のアラート（`> [!NOTE]`、`> [!WARNING]` など）: GitHub 以外では `[!NOTE]` が文字列のまま表示される。警告・必須事項は本文の語句をボールドにする。

### 文字

- 英数字は半角、カタカナは全角にする。
- 和文と英数字・インラインコード・UI 要素の `[ ]` の間には半角スペースを入れる（`AI が 1 行で返す`、`` `foo` を返す ``）。Markdown はテキストのまま読まれることが多く、語の切れ目がわかりやすいため。
- 全角の句読点・括弧（、。「」『』（）など）の隣には入れない（「AI」、AI。）。

### リスト

- 項目が文なら文末に「。」を付け、体言止めなら付けない。同じリストの中で形をそろえる。
- 下位のリストを導く項目は「：」で終えてよい。

### コードブロック

- 言語を必ず指定する（` ```bash `、` ```json ` など）。該当する言語がなければ `text` にする。

### リンクと画像

- リンクテキストは行き先を表す語句にする。「こちら」「ここ」にしない。読み上げやリンクの一覧では、前後の文がなく行き先がわからないため。
- 画像には内容を表す代替テキストを付ける（`![構成図](arch.png)`）。

### 使ってよい記法

引用、リスト、コードブロック、インラインコード、罫線、リンク、画像、打ち消し線、テーブル。リスト・コードブロック・リンク・画像の書き方は、それぞれの節に従う。

### 折りたたみ（`<details>` / `<summary>`）

条件つきで使ってよい。問題は記法ではなく、内容を隠すことにある。ページ内検索（Ctrl+F）が閉じた中身を見つけない実装があり、PDF への書き出しで落ちることがあり、上から順に読めなくなる。

- 使ってよいのは、本筋に必須でない長い補足だけ。例: 長いログやコマンドの出力、上級者向けや例外ケースの詳細、トラブルシューティングや FAQ の付録。
- 作業を終えるために必ず読む手順やエラーの対処は折りたたまない。
- 開かないと文書がほぼ空になる使い方はしない。

## 作成モードの出力

- 文書を GFM の Markdown で出力する。H1 は「文書の種類」に従う。
- タイトルの直後に、文書の内容を要約するリード文を 1〜2 文置いてよい。
- 出力する前に、検査スクリプトに通す。検出されたものは直し、誤検出なら理由を確認したうえで残す。
- ファイルで渡す指示があれば `.md` で保存する。短いものは会話の中で示してよい。

## レビューモードの出力

まず検査スクリプトを実行し、その結果とスクリプトで判定できないルールの確認を合わせて、指摘レポート、修正済みの Markdown の順に出力する。ファイルを直接直すよう頼まれたときは、修正済みの Markdown を出す代わりにファイルを編集する。

### 1. 指摘レポート

違反ごとに、箇所・ルール・問題・修正案を表にする。箇所は行番号か短い引用で示す。

```markdown
## レビュー結果

| 箇所 | ルール | 問題 | 修正案 |
|---|---|---|---|
| 5 行目 `# 手順` | 見出し | タイトル以外に H1 を使っている | `## 手順` にする |
| 「重要：〜」の段落 | 強調の乱用 | 段落全体がボールド | 「削除すると復元できません」だけをボールドにする |
| `"本番"` | ダブルクォーテーション | 日本語に `"` を使っている | 「本番」にする |
```

- 違反がなければ「指摘なし」と書き、良い点を一言添える。
- ルール外の明らかな誤り（壊れたリンク、閉じていないコードブロックなど）は、「参考」として別に挙げる。スタイルの違反と混ぜない。

### 2. 修正済みの Markdown

指摘をすべて反映した全文を、そのまま貼り付けられるようにコードブロックで出す。

内容の意味は変えない。ルールに合わせる整形だけを行い、文章の書き換えや情報の追加・削除はしない。整形を超える変更が必要なら、修正済みの Markdown には入れず「提案」として別に挙げる。

## 判断に迷ったら

- UI 要素を `[ ]` とインラインコードのどちらにするかなど、表の分類はチームの運用で揺れる。渡された文書やリポジトリの既存の文書に一貫した慣習があれば、それを尊重しつつルールとの差分を指摘する。
- ルールが想定していないケース（新しい記法の是非など）は断定しない。ルールの意図（移植性・可読性・アウトラインの健全性・アクセシビリティ）に照らして判断し、根拠を添える。
