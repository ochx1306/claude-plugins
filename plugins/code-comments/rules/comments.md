## コメントの原則
- 読者は、会話や変更経緯を知らずに初めてこのファイルを開く人である。ほかのリポジトリとの比較や、改修前の状態を前提にした説明は書かない。
- コードを読んでもわからないこと（理由・制約・前提）だけを書く。
- 変更経緯はコメントに書かず、コミットメッセージや PR 説明に書く。
  コードを読む人に必要な理由は「〜のため〜する」と現在の制約として書く。
- コードをそのまま言い換えるだけのコメント、フレームワークの決まった挙動をなぞるコメント、区切り線・見出しだけのコメントは書かない。既存のコードに同じものがあっても真似しない。
- 付けている対象の責務の範囲だけを書く。定数や関数のコメントに、それを使う側の挙動や結果を書かない。
- 目的だけでなく、それが何かを書く。変数や定数は「何か・どう使うか・なぜか」の順に書く。
- パスやメソッド名を括弧で添えない。定数の値は docblock に書かず、定数名で指す。移動や変更でコメントだけが古くなるため。
- 処理のまとまりを要約するコメントと、それが指すコードの間に別のコメントを挟まない。理由は要約のすぐ下に書く。

## コメントの言葉
- 動詞は比喩や口語を使わず、起きることをそのまま書く（積む → 追加する、触る → 参照する）。
- 1 つの概念は 1 つの言葉で呼び、ファイル全体・PR 全体でそろえる。画面の機能は画面名で呼ぶ。
- 修飾のかかり先が二通りに読める文は、文を分ける。
- 理由が複数あるときは、並べるだけにせず「そのため」「ただし」などでつなぐ。

## コメントの見直し
- 既存のコメントを消す案を出す前に、同じ書き方が慣例になっていないかを grep で確かめ、件数を添える。慣例なら残す。
- コメントへの指摘を受けたら、同じ傾向を変更全体で探す。

## docblock の書式
- 日本語の常体で書く。
- summary は 1 文で書き、文末に「。」をつけない（例: `ユーザー ID から表示名を返す`）。
- summary・詳細・タグのかたまりの間には空行を 1 行入れる。詳細がないときも summary とタグの間に入れる。

```
/**
 * ユーザー ID から表示名を返す
 *
 * 退会済みのユーザーは表示名を空にしているため、代わりに「退会済み」を返す。
 *
 * @throws NotFoundError ユーザーが存在しないとき
 */
```
